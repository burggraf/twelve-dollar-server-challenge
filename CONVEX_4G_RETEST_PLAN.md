## Goal

Determine whether the official self-hosted Convex backend can sustain the canonical HTTP workload within **one aggregate 1-vCPU / 4-GiB / no-swap serving budget**, and establish a confirmed capacity if possible.

A valid result may be a modest confirmed capacity, a confirmed lower bound, or an accurately diagnosed blocker. Do not assume that Convex must reach 2,500 users, that 4 GiB is sufficient, or that tuning will succeed.

Keep three questions separate:

1. **Fit and stability:** can the full canonical dataset and supported native application operate without uncontrolled resource growth?
2. **Capacity:** what load satisfies the existing latency/error requirements repeatedly?
3. **Lifecycle:** can the deployment stop cleanly and preserve acknowledged writes? A throughput pass does not repair a lifecycle failure.

## Definition of done

Either:

- A fully audited, correctly labelled capacity/lower-bound result with three independent passing confirmations on frozen inputs, plus an explicit lifecycle verdict; **or**
- A bounded, evidence-backed blocker report distinguishing application/worker/database/resource/lifecycle failure from runner or host invalidity.

A smoke pass, an apparent tuning improvement, or “it did not OOM this time” is not completion.
